## The counter matches the log; the guard does not gate the read

`_count_previous_reads` counts `## Read ` headings, falls back to legacy `| 2` table rows, and raises `SystemExit` when a log exists with neither. Against the current file that is 3 headings and 0 legacy rows, so the heading branch decides and the legacy branch cannot double-count a mixed file. `results.json` carries `access_log_entries: 3`, `verify_submission.py` reads the same 3, and the DISCLOSURE integrity note fires because `previous_entries` is non-zero.

The ordering is the problem:

```
546   holdout = load_test_holdout(HOLDOUT_ACKNOWLEDGEMENT, config.data_dir)   # sealed read
...
600   figures = _figures(output_dir / "figures", labels, calibrated, replay, holdout, ...)
604   access_log = output_dir / "ACCESS_LOG.md"
605   previous_entries = _count_previous_reads(access_log)                     # tripwire
```

`_figures` writes `precision_recall.png` from held-out labels and `risk_density_timeline.png` with the sealed spike and benign windows shaded. The branch that "refuses to run" therefore refuses after the labels have been read and after two derived artifacts have been published, and it returns before `results.json` and the `ACCESS_LOG.md` append. What the honesty ledger gets is a read that happened, produced on-disk artifacts, and left no entry — the failure mode the counter exists to make impossible. README's "refuses to run rather than understate an unparsed log" describes the intent accurately and the timing loosely.

## The Postgres drill asserts on the real ingestion path

`drill_postgres_down` builds a session double whose `scalars`, `execute`, and `commit` all raise `OperationalError`, hands `TransactionService` a publisher that records event types, primes the service on 2,000 real validation rows, then ingests row 2,001 and asserts four things together:

```python
error.code == "database_unavailable"
error.http_status == 503
state.get("postgres").status == "down"
buffered == ["transaction.buffered"]
```

Those land on production code: `_database_unavailable` publishes `transaction.buffered` to the transactions topic then raises `AppError("database_unavailable", …, 503)`, and `main.py` maps any route-level `SQLAlchemyError` to the same code.

Not tested: no pytest file references the Postgres-down path, the buffering behaviour, or the read counter. Both are exercised only by `scripts/failure_drills.py` and by running the evaluation.

## The health fallback covers the outage but not the first load

`api.health()` probes Postgres inside a try/except, marks the dependency, pings the cache, and returns a 200 snapshot, so it survives the outage that 503s the summary endpoint. The double-failure path then rewrites the previous snapshot's keys to `down` with reason `health probe unreachable` and sets `connection: offline`. Because that key set comes from what the client already holds, a cold start during a full outage has nothing to rewrite and the strip renders its empty state instead of naming the unreachable dependencies.
