# DB-backed, human-gated Phase 6 policy lifecycle

The Phase 6 hardening closes four of the five prior blockers end to end: DB activation controls serving, promotion evidence is identity-bound, authoritative outcomes produce atomic reward/memory state, and corrupt production or candidate artifacts fail safely. Outcome and reward Kafka events now use transactional outbox rows, but analyst-decision publication still occurs after its durable state commit and can be lost permanently. The original authority, shadowing, promotion, memory, holdout, and action-effect provenance guarantees remain intact. **Watch for: confirmed — a completed analyst decision can return a publish error after commit, and an idempotent retry returns the stored decision without republishing it.**

**Verdict**: NEEDS_CHANGES

## High-level view

Serving disconnected from DB activation is resolved. `RuntimePolicyResolver` reads the active `PolicyVersion` for every score, verifies its DB checksum and assumptions version, and caches only by version/checksum identity, so promotion and rollback affect existing application instances without restart.

Promotion evidence unbound from the promoted policies is resolved within the trusted DB/artifact control plane. The gate validates the same-holdback evidence digest, holdback digest, action-effect version, candidate checksum, production identity, and any supplied version identities before verifying artifacts and compare-and-set activation.

Post-commit loss is resolved for the learning chain, not every Phase 6 event. Outcome and reward events enter `outbox_events` in the same transactions as outcome and reward/memory state; `analyst.decision` is still sent directly after decision completion commits.

Conflicting outcome and reward-memory divergence is resolved. Outcome recording admits one immutable payload, evaluation reloads the authoritative decision, reward replay validates immutable inputs behind a unique key, and memory changes only with a newly created reward in the same transaction.

Corrupt production and shadow artifacts are isolated. Production failure selects conservative human escalation and marks degradation; candidate failure removes only its observational ranking and cannot alter or block the production action.

The authority boundary remains deterministic and human-gated. The LLM only explains an immutable production ranking, the graph records `authorized: false`, and review recomputes policy with the authenticated role. Candidate output, incident memory, and learned rankings remain advisory; promotion and rollback have route- and service-level admin checks, with no automatic promotion path.

## Active DB policy now drives every incident

`main.py` injects `RuntimePolicyResolver` into the investigation graph. Each score queries `LearningRepository.active_policy_version` and loads that row’s artifact with its assumptions version and checksum (`backend/app/services/policy_service.py:89-151`). The cache key includes `policy_version_id` and checksum, preventing an activated row from reusing the former production model.

Activation locks the `Policy` row and checks the active version observed before promotion or rollback. Both operations supply that expected ID, closing the stale-read race; tests exercise two existing resolvers across promotion and a new resolver after rollback.

## Promotion evidence follows both policy identities

The evidence contains both metric sets, frozen holdback manifest and digest, assumptions version, candidate checksum, production identity, optional version numbers, and an overall digest (`backend/app/services/policy_service.py:31-60`). `PolicyService._evidence` recomputes and compares these values to the candidate and current production rows before metric parsing; promotion then verifies both artifacts, and activation rejects a production pointer changed after validation (`backend/app/services/policy_service.py:321-380`). The built-in conservative policy uses a stable identity tied to fixed human-escalation behavior.

**Confirmed operational limitation, not a correctness blocker:** SHA-256 establishes integrity within the trusted DB/artifact control plane, not authenticity against an actor able to rewrite both rows and evidence. That stronger threat model would require signed evidence and artifacts.

## Outcome learning is atomic, but analyst-action publication is not

`FeedbackService.record_outcome` compare-and-sets the decision, updates incident/audit state, and enqueues `analyst.outcome` before commit (`backend/app/hitl/feedback_service.py:43-84`). `EvaluationService.handle_outcome` reloads and validates the authoritative decision, writes the reward, updates memory only for a new reward, and enqueues `reward.calculated` before commit (`backend/app/services/evaluation_service.py:194-298`). Kafka downtime therefore leaves retryable outbox rows.

Reward replay compares incident, decision, action, amount, components, assumptions, kind, and run ID when its idempotency key already exists. Conflicting replay raises, while the outcome compare-and-set distinguishes an identical retry from a different second outcome, preventing competing payloads from splitting reward and memory state.

The remaining **confirmed** blocker is at `backend/app/hitl/review_service.py:88-91,145-147,258-293,358-367`. `_complete_resume` commits `completed`, then `_publish` sends directly. On Kafka failure the request fails after commit; retry hits the completed-decision shortcut and never republishes. WebSocket failure can likewise turn committed success into an API error. Queue the Kafka event inside `_complete_resume` and catch local broadcast failures as best effort.

## Corrupt artifacts fail closed without contaminating shadow serving

Artifact loading hashes the complete byte stream and deserializes those verified bytes; policy loading also validates schema, actions, features, and action-effect version. Production load/scoring failure selects the conservative ranking led by `human_escalation` and marks degradation.

Candidate loading and scoring use a separate error channel. Missing, corrupt, incompatible, or failing candidates produce no candidate ranking and set candidate degradation, while `operative_action` remains production-derived. Activation exists only in `PolicyService`, not `ShadowPolicy`.

**Confirmed operational limitation, not a correctness blocker:** verified models are cached under immutable DB identity. Replacing bytes without changing the DB checksum does not evict an already loaded model, while a cold loader detects the mismatch; artifact storage must remain immutable.

## Learned and LLM outputs remain recommendations

`ResponseAgent` derives actions from `production_ranking`, asks the LLM only for explanations, then reconstructs responses by iterating the original list with `requires_human_review=True` (`backend/app/agents/nodes/response_agent.py:42-105`). Unknown, omitted, or reordered LLM actions cannot enter the result.

The graph stores `authorized: false` and interrupts for human review (`backend/app/agents/graph.py:62-101`). Review resolves the human’s final action, rebuilds authorization context from deterministic evidence and impact, reruns `PolicyEngine` with `actor_role`, blocks deny decisions, and records `human_policy_gate` only for passing approve/modify choices (`backend/app/hitl/review_service.py:151-188`). Default-deny role permissions prevent an analyst from authorizing lead/admin-only actions through modification.

Promotion and rollback require `admin` in FastAPI and repeat that check against the permission map in `PolicyService`. Evaluation and shadow scoring never invoke activation. Incident memory contributes advisory evidence and two ranking features but is absent from authorization context, so its effect ends at the recommendation checked by deterministic policy and a human.

## Chronological development holdback preserves explicit provenance

`build_offline_incidents` loads only train and validation, sorts incidents chronologically, and attaches the action-effect version. `chronological_policy_split` holds back the final configured validation fraction and excludes those IDs from fit; evaluation reconstructs the split. `load_test_holdout` has no caller outside its boundary and negative guard test.

The strict action-effect schema requires `explicit_counterfactual_assumptions`, INR, a notice, and exactly six actions. Calculated and observed reward records retain assumptions, source, notice, currency, weights, and version; reward/policy artifacts and promotion evidence reject a different version.

## Validation leaves the remaining loss path uncovered

Validation passed: 17 focused unit tests for promotion, reward/outbox replay, artifact integrity, and agent gating, plus one streaming integration test. **Not tested (confirmed gap tied to the blocker):** no failure-injection test requires `analyst.decision` to survive publisher failure after completion; add a restart/retry test analogous to outcome/reward outbox recovery.
