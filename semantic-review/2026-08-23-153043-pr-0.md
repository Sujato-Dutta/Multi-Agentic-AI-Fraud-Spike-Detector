# Phase 5 safety fixes with recovery and concurrency gaps

The follow-up confirms that all five prior findings are resolved on their intended normal paths: authorization no longer consumes model verifier scores, segment breadth uses the full incident window, stable-policy retries reconcile an advanced checkpoint, both incident views suppress rejected hypotheses, and identical requests serialize within one process and on Postgres. Three failure-path defects remain blocking: malformed numeric evidence can be accepted after lossy coercion, recovery can reject its own persisted review after a policy or authorization-version change, and the Postgres ownership lock is held while graph work opens nested database sessions, allowing connection-pool starvation. SQLite multi-process ownership and direct post-commit publication remain narrower deployment and distributed-delivery limitations.

Watch for: **confirmed, High** lossy count parsing marks malformed authorization evidence valid; **confirmed, High** advanced-checkpoint recovery depends on recomputing an identical mutable policy snapshot; **confirmed, High** the decision row transaction spans nested graph persistence and can starve a bounded connection pool; **likely, Medium** SQLite cannot serialize identical requests across processes; **confirmed, Medium** committed decisions have no durable publication handoff.

**Verdict**: NEEDS_CHANGES

## High-level view

The model-controlled grounding and self-denominated breadth findings are resolved. `policy_gate` and `ReviewService._decide_locked` now authorize from deterministic window, segment, impact, and history records; model verification controls claim display, while breadth is selected-segment support divided by full-window transaction count.

The split-state recovery and display-leak findings are resolved under a stable deployment. A `resume_pending` decision can reconcile a checkpoint at `awaiting_outcome`, and both `incident_detail` and `investigation_detail` apply the fail-closed claim projection.

**Confirmed, High:** `build_authorization_context` uses permissive `int()` and `float()` conversion. Fractional and negative fractional counts can truncate into valid values, producing grounding and confidence scores of 1 instead of failing closed.

**Confirmed, High:** `ReviewService._decide_locked` recomputes authorization and policy output before comparing an existing `resume_pending` row with the checkpoint. A policy, builder-version, or normalization change can make the new `final_action` differ from the persisted review and permanently turn recovery into a conflict.

**Confirmed, High:** Postgres serialization keeps `FeedbackRepository.get_for_update` open while `_decide_locked` awaits graph resume and `InvestigationService._persist`. Each resume needs additional database sessions, so concurrent incidents can occupy the bounded pool with owner sessions and leave every owner waiting for another connection.

**Likely, Medium:** `_decision_locks` close the identical-request race within one process, and Postgres `FOR UPDATE` closes it across instances. SQLite omits `FOR UPDATE`, leaving separate processes without shared ownership.

**Confirmed, Medium:** completion commits before `ReviewService._publish`, with no outbox or delivery marker. A crash or send failure loses the event because terminal-row retries return without publishing; broker success followed by local-broadcast failure also leaves subscribers inconsistent.

## High — Authorization accepts malformed counts after lossy coercion

**Confirmed.** `build_authorization_context` in `backend/app/safety/evidence_grounding.py` converts window count, segment support, and similar-incident count with `int()` and monetary values with `float()`, then validates only the converted values. A focused probe using `window_count=100.9`, `segment_support=-0.5`, and `similar_count=-0.5` produced counts of `100`, `0`, and `0`, `basis.valid=True`, and grounding/confidence scores of `1`. Python also treats booleans as integers and some boolean/numeric pairs as equal during impact comparison.

Malformed checkpoint records can therefore normalize into a narrower segment and pass policy instead of forcing escalation. Validate the four required payloads with strict typed models, reject booleans, numeric strings, fractional counts, negative values, and every non-finite monetary field, and compare canonical validated records. Add malformed-type and fractional/boolean fixtures to the `build_authorization_context` tests.

## High — Advanced-checkpoint recovery depends on mutable policy output

**Confirmed.** `ReviewService._decide_locked` in `backend/app/hitl/review_service.py` loads a `resume_pending` row without requiring the graph still to be paused, then rebuilds `policy_context`, `policy_basis`, `policy`, and `final_action` from current code and configuration. `ReviewService._ensure_same_decision` compares that document with the stored row before recovery, while `ReviewService._ensure_matching_checkpoint_review` later requires equality with the checkpointed review.

The crash test covers recovery only while those derivations remain byte-for-byte stable. If a deployment changes the policy version, thresholds, authorization-basis version, or normalization, retry raises `review_already_decided` or `review_checkpoint_conflict` before `InvestigationService.reconcile`. For an existing pending decision, verify immutable request identity, reconstruct the review from `AnalystDecision.original_recommendation` and `AnalystDecision.final_action`, and use that persisted snapshot for checkpoint matching. Add a recovery test that changes active policy after the simulated post-resume crash.

## High — Resume ownership holds one connection while requesting more

**Confirmed.** `FeedbackRepository.get_for_update` in `backend/app/db/repositories.py` acquires the Postgres decision-row lock, and `ReviewService._decide_locked` keeps that session open across `_review_state`, `InvestigationService.resume` or `continue_from_checkpoint`, and `InvestigationService.reconcile`. Graph finalization can call the LLM, while `InvestigationService.resume` and `_persist` open separate sessions for incident lookup and projection persistence.

With a bounded pool, enough reviews for different incidents can each retain one owner connection and wait for an additional connection that cannot be returned until an owner finishes. Replace the long `FOR UPDATE` scope with a short compare-and-set from `resume_pending` to a leased `resuming` state, commit before graph work, then complete or release it in another short transaction. Exercise more concurrent incidents than pool capacity and verify owner-loss recovery and one graph resume per decision.

## Medium — SQLite has no cross-process resume owner

**Likely.** `ReviewService.decide` uses an `asyncio.Lock` in `_decision_locks`, which serializes identical submissions only inside one process. `FeedbackRepository.get_for_update` compiles to `FOR UPDATE` on Postgres but an ordinary `SELECT` on SQLite, so separate SQLite workers can both observe `resume_pending` and reach graph resume/publication; exact duplication depends on checkpoint placement and request affinity.

The production path defaults to Postgres, while SQLite falls back to a non-durable in-memory checkpoint and disables approve/modify, so this is a deployment limitation rather than a Postgres blocker. Make SQLite explicitly single-process/test-only, or use an atomic status/lease update whose affected-row count provides ownership on both databases.

## Medium — Completed decisions can lose their publication

**Confirmed.** `ReviewService._decide_locked` commits `row.status = "completed"` and the `investigation_resumed` audit event before calling `ReviewService._publish`. A stop in that gap or either publisher raising leaves the next identical request on the early terminal-row return. Broker delivery also precedes `local_publisher`, so local broadcast can fail after the durable broker accepted the event.

Postgres and the checkpoint remain authoritative, but the action event is at-most-once and broker/WebSocket subscribers can diverge. Persist a transactional outbox row keyed by `decision_id`, dispatch with retry, require consumer idempotency, and make WebSocket delivery a projection of the durable event.
