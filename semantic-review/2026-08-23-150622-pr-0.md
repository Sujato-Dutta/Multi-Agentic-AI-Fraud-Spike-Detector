# Phase 5 human-review safety and recovery boundary

Phase 5 adds a durable human-review interrupt, deterministic policy evaluation, analyst decision persistence, evidence-grounded display filtering, and Postgres-failure buffering through the transaction stream. `authorized` remains false until an analyst approves or modifies a recommendation and the action is reevaluated against role and policy limits. However, policy still trusts an LLM verifier for grounding and confidence, while decision/resume crash and concurrency windows can strand or duplicate an authorized decision. Normal segment breadth is also calculated as approximately 1.0, and the incident timeline bypasses the claim filter used by the investigation endpoint.

Watch for: **confirmed** LLM verifier output can satisfy grounding/confidence policy gates; **confirmed** a post-resume crash can permanently strand a committed decision in `resume_pending`; **confirmed** incident timelines expose raw rejected hypotheses; **confirmed** segment breadth uses the selected segment as its own denominator; **likely** concurrent identical submissions can resume and publish the same authorized decision more than once.

**Verdict**: NEEDS_CHANGES

## High-level view

Monetary impact, segment support, transaction counts, and incident novelty originate in deterministic database-backed tools. Claim support is the exception: the secondary LLM's `supported` verdict is accepted after citation-ID resolution and becomes both `grounding_score` and `confidence_score`, so an LLM-controlled value decides whether those policy floors pass.

Breadth divides the leading segment's support by the deterministic impact count for that same selected segment. Those counts normally describe the same cohort, producing 1.0 and denying executing responses under the configured 0.25 global ceiling rather than measuring the segment against the full incident window.

Committing the decision as `resume_pending` before LangGraph resume preserves the analyst choice across an early failure. Recovery stops working once the durable checkpoint advances: a retry is rejected before it can reconcile the pending database row.

One deterministic decision ID per incident and equality checks reject conflicting terminal choices. No compare-and-set owner exists for a `resume_pending` row, so identical concurrent retries can independently reach checkpoint resume, audit completion, and broker publication.

The investigation endpoint filters root-cause hypotheses, but the general incident timeline returns persisted agent-output payloads directly. API-originated Postgres failures are buffered to the transaction topic while stream retries disable buffering, preventing a consumer republish loop. Unknown roles and actions resolve to empty permissions or `deny`, and policy is reevaluated with the authenticated role before authorization.

## Critical — LLM verifier verdicts become authorization inputs

**Confirmed.** `VerificationAgent.__call__` in `backend/app/agents/nodes/verification_agent.py` checks that each model-produced verdict has one known claim ID and that the claim cites existing evidence IDs, but otherwise copies `suggestion.verdict` into `VerificationVerdict`. It never deterministically establishes that the cited evidence supports the claim. `EvidenceAgent` also lets an LLM choose each hypothesis statement and available citation, so the verifier can mark a model-authored claim `supported` merely because its citation resolves.

`ground_claims` in `backend/app/safety/evidence_grounding.py` treats that verdict as support, and `policy_gate` in `backend/app/agents/graph.py` assigns the ratio to both `grounding_score` and, when not degraded, `confidence_score`. `ReviewService.decide` in `backend/app/hitl/review_service.py` reevaluates the approved action using those checkpointed scores. Human approval and deterministic action/role, monetary, and breadth limits prevent direct autonomous authorization, but the LLM can make two policy safety floors pass and materially influence whether an analyst-approved defensive action is authorized.

Authorization grounding needs deterministic claim-specific predicates or another non-model source. If semantic support cannot be established deterministically, verifier output should remain advisory and unresolved support should fail closed for executing actions.

## High — Segment breadth compares the segment with itself

**Confirmed.** `policy_gate` in `backend/app/agents/graph.py` calculates breadth as `segment_statistics.support / impact.transaction_count`. `get_cost_estimate` in `backend/app/agents/tools.py` builds `impact.transaction_count` by applying the first persisted segment's conditions to incident transactions, while `get_segment_stats` reads support for that same first segment. Segmentation computes support from transactions matching those conditions, so the normal ratio is 1.0; the fallback segment also uses the full-window count in both places.

With `segment_breadth_ceiling: 0.25` in `infrastructure/policies.yaml`, executing actions reach `segment_breadth_ceiling` denial even when the segment is a small part of the window. `no_action` and `human_escalation` bypass the threshold as non-executing workflows, which is why the rejection-only end-to-end path succeeds. The denominator should be the `window_statistics` transaction count, with narrow-pass and broad-deny coverage.

## High — Durable resume can leave a decision permanently pending

**Confirmed.** `ReviewService.decide` commits the analyst decision and audit event with status `resume_pending`, calls `InvestigationService.resume`, and only afterward marks the row `completed`. If the durable checkpoint advances to `awaiting_outcome` but the process fails before the second database commit, the choice remains `resume_pending`.

A retry cannot repair that split state because `decide` calls `_pending_state` before handling the pending row, and `_pending_state` accepts only `awaiting_human_review`. The graph now reports `awaiting_outcome`, so retries return `review_not_pending`; completion audit and publication are also lost. Reconciliation should detect the same review in the checkpoint, idempotently complete the row/audit/outbox, and return without another resume.

## High — Incident timeline bypasses rejected-claim filtering

**Confirmed.** `_display_payload` in `backend/app/api/routes/incidents.py` strips unsupported and contradicted hypotheses from `/incidents/{incident_id}/investigation`. `/incidents/{incident_id}` instead returns `IncidentRepository.timeline`, which places every `AgentOutput.payload` into the response without filtering. Because `InvestigationService._persist` stores raw `root_cause_hypotheses` for audit, analysts receive unsupported or contradicted statements through incident detail.

Raw outputs can remain in audit storage, but every analyst-facing serializer needs the same grounding boundary. The timeline should omit raw agent payloads, apply filtering with persisted verification, or move unfiltered material behind a separately authorized audit-only endpoint.

## High — Identical concurrent decisions have no single resume owner

**Likely.** `_decision_id` in `backend/app/hitl/review_service.py` gives one primary key per incident, and `_ensure_same_decision` rejects a conflicting request after one row wins. For an identical request against `resume_pending`, both callers continue; no compare-and-set transition, lease, or lock grants only one caller permission to invoke `InvestigationService.resume`.

Graph duplication depends on checkpointer concurrency behavior, but the service has no exactly-once boundary. Both successful callers can run completion, `AuditRepository.append_once` has a read-before-insert check without a database uniqueness constraint, and `_publish` sends directly without an outbox or publisher idempotency key. A downstream action consumer can therefore receive duplicate `analyst.decision` events. Resume ownership should be claimed atomically, audit idempotency enforced in the database, and publication moved to a transactional outbox keyed by `decision_id`.
