# Phase 6 offline reward learning and human-gated policy lifecycle

Phase 6 adds deterministic counterfactual rewards, offline LinUCB ranking, production-versus-candidate shadow scoring, incident memory, and an admin-gated policy registry. Learned and LLM output stay outside action authorization: deterministic evidence, policy rules, role permissions, and durable human review remain authoritative. The chronological development holdback and sealed test-label loader preserve the declared evaluation boundary. Promotion, artifact failure, and outcome replay do not yet preserve those guarantees end to end.

Watch for: **confirmed** serving does not switch when a policy is promoted or rolled back; **confirmed** promotion evidence is not bound to a deployable artifact or shared holdback; **confirmed** shadow/corrupt artifacts can stop the operative path instead of degrading conservatively; **confirmed** post-commit publication and concurrent outcome handling can lose or rewrite learning events.

**Verdict**: NEEDS_CHANGES

## High-level view

The response agent restores the production ranking after LLM generation, deterministic evidence builds authorization inputs, and human review re-evaluates the selected action with the actor role. Learned `expected_reward_inr` values are advisory estimates and never enter deterministic incident impact, observed-reward accounting, or authorization.

Database activation is serialized under a row lock and version status, active pointer, approval metadata, and audit are committed together. That transaction is disconnected from the startup-loaded `ShadowPolicy`, so promotion and rollback change registry metadata without changing the policy used for new incidents.

Rewards have a unique idempotency key and exact duplicate outcome requests are recognized. Delivery is not atomic with persistence: outcome and reward events are published after commit while replay suppresses re-publication, and immutable outcomes use a race-prone read-then-write sequence.

Training reserves the chronological validation tail from bandit fitting and never calls the guarded test-label loader. Action effects are strict, versioned INR assumptions, although individual counterfactual payloads omit the top-level notice/source/currency.

Missing production policy artifacts select a conservative fixed ranking. Corrupt policy artifacts abort startup, shadow scoring failures are not isolated, and stored artifact checksums are not verified before `joblib.load`.

<summary>Issues (8)</summary>

1. **Serving activation is disconnected (confirmed, must fix)** — Promotion and rollback update database metadata but never atomically switch the `ShadowPolicy` used by investigations. Resolve the active artifact from the registry and make promotion/rollback update serving behavior with rollback-safe activation.
2. **Promotion evidence is unbound (confirmed, must fix)** — Nullable artifact fields and metrics without artifact, holdback, assumptions, evaluator, or comparator identity allow shape-valid but unrelated evidence to pass. Require an immutable same-holdback evaluation record tied to both artifact checksums.
3. **Outcome and reward delivery can be lost (confirmed, must fix)** — Both services commit before publishing, while duplicate replay suppresses re-publication. Use a transactional outbox or persisted delivery state so retries complete publication.
4. **Outcome immutability and replay consistency can diverge (confirmed, must fix)** — Concurrent outcome writes can overwrite each other, and conflicting event replay can retain the first reward while replacing incident memory. Use compare-and-set outcome persistence and validate events against the authoritative stored outcome.
5. **Shadow and corrupt artifacts are not isolated or verified (confirmed, must fix)** — Candidate scoring errors can block production, corrupt policy files abort startup, a corrupt reward file can be reported healthy, and registry checksums are ignored before `joblib` deserialization. Isolate shadow failures, validate/checksum artifacts before load, and fall back conservatively where serving can remain safe.
6. **Learned INR values need estimate semantics (confirmed, acceptable limitation)** — `expected_reward_inr` is a learned advisory estimate rather than deterministic financial accounting. Preserve that distinction in every API/UI representation and keep the value outside authorization.
7. **Counterfactual disclosure metadata is incomplete (confirmed, non-blocking)** — Individual results omit the action-effect notice, source, and currency. Include them in each result or enforce a versioned join in every renderer.
8. **Safety failure paths are untested (confirmed, significant coverage gap)** — Add regression tests for serving activation, artifact integrity/corruption, failed publication replay, concurrent outcomes, and reward/memory consistency.

### Deterministic evidence and human review remain authoritative

`ResponseAgent` uses only `production_ranking`, asks the LLM to explain without reordering, then rebuilds responses in the original order and filters citations (`backend/app/agents/nodes/response_agent.py:34-42`, `:58-65`, `:74-103`). The pre-review gate derives a deterministic authorization context and records `authorized: False` before the interrupt (`backend/app/agents/graph.py:63-84`). Review recomputes that context with the actor role and authorizes approve/modify only after `PolicyEngine` evaluation (`backend/app/safety/evidence_grounding.py:74-225`; `backend/app/safety/policy_engine.py:82-145`; `backend/app/hitl/review_service.py:156-190`).

Promotion and rollback require a live authenticated admin at the route and repeat the default-deny permission check in `PolicyService` (`backend/app/api/routes/models.py:13-16`, `:52-67`; `backend/app/core/security.py:61-86`; `backend/app/services/policy_service.py:134-138`). Activation callers are limited to those explicit service methods; no scheduler or automatic promotion path was found (`backend/app/services/policy_service.py:60-131`).

A learned policy does produce `expected_reward_inr` estimates (`backend/app/ml/policy/contextual_bandit.py:57-78`). **Confirmed, acceptable limitation:** this deliberate model score is used for ranking and promotion evaluation but not deterministic impact, observed reward, or authorization. It needs estimate/assumptions labeling wherever exposed so it is not presented as a computed financial actual.

### Promotion changes registry state but not the serving policy

**Confirmed, must fix:** `main.py` constructs one `ShadowPolicy` from fixed production/candidate paths and injects it into the investigation graph for the application lifetime (`backend/app/main.py:77-82`, `:133-151`, `:241`). Promotion and rollback only call `LearningRepository.activate_version`, updating database status, active pointer, approver, and timestamps (`backend/app/services/policy_service.py:60-131`; `backend/app/db/repositories.py:824-849`). They never verify, copy, reload, or atomically swap the selected `artifact_uri`; restart also reads the fixed configured path rather than the active database version. Database activation is atomic, but behavioral activation and rollback do not occur.

The tests assert database status and audit changes only (`tests/unit/test_policy_promotion.py:86-131`, `:164-201`), so they pass while serving continues to use the old policy.

### Promotion evidence is not bound to an artifact or common holdback

**Confirmed, must fix:** `PolicyVersion.artifact_uri` and `artifact_checksum` are nullable, and promotion validates only candidate status plus shape-valid JSON metrics (`backend/app/db/models/entities.py:249-270`; `backend/app/services/policy_service.py:60-100`). Tests promote candidates with no artifact (`tests/unit/test_policy_promotion.py:99-117`). The `measured_holdback` gate checks only `candidate.evaluated_incidents > 0`; metrics contain no holdback/data fingerprint, assumptions version, evaluator version, comparator identity, or artifact checksum (`backend/app/ml/policy/shadow_policy.py:18-60`). Shape-valid metrics can therefore activate an unrelated or absent artifact.

The evaluator names an always-`human_escalation` chooser as `production` instead of loading the active production artifact (`evaluation/evaluate_policy.py:74-91`). This matches the declared initial baseline, but **confirmed, must fix for subsequent promotions:** later candidates are not compared with actual production on the same holdback. Require an immutable evaluation record binding both artifact checksums to the same incidents, assumptions, and evaluator version.

### Outcome replay is row-idempotent but not delivery-safe

The reward table uniquely constrains `idempotency_key`, and insertion handles existing rows and races (`backend/app/db/models/entities.py:275-300`; `backend/app/db/repositories.py:628-669`). The key includes decision ID and action-effect version (`backend/app/services/evaluation_service.py:205-215`).

**Confirmed, must fix:** `FeedbackService` commits outcome and audit before publishing (`backend/app/hitl/feedback_service.py:62-76`). If publish fails, retry takes the duplicate-return branch before `_publish`, so reward calculation is never retriggered. `EvaluationService` likewise commits reward and memory before publishing and publishes only when `created` is true (`backend/app/services/evaluation_service.py:205-248`); after a publish failure, Kafka replay sees `created == False`, skips the event, and allows the input offset to commit. Use a transactional outbox or persisted delivery state at both boundaries.

### Concurrent or conflicting outcome delivery can rewrite learning state

**Confirmed, must fix:** outcome immutability is a read-then-write without a lock, version predicate, or terminal-outcome constraint. Concurrent requests can both observe no outcome, after which `FeedbackRepository.record_outcome` unconditionally overwrites outcome and status (`backend/app/hitl/feedback_service.py:45-63`; `backend/app/db/repositories.py:550-567`). Last commit wins.

`EvaluationService.handle_outcome` trusts the event payload rather than the authoritative decision. On conflicting replay, `record_reward` returns the original reward but `upsert_memory` still replaces summary, attributes, and tags from the new payload (`backend/app/services/evaluation_service.py:166-232`; `backend/app/db/repositories.py:670-696`). **Confirmed, must fix:** reward and memory can describe different outcomes for one decision. Use compare-and-set persistence and load or hash-check the authoritative outcome in the handler.

### Shadow and corrupt artifacts are not isolated conservatively

**Confirmed, must fix:** `ShadowPolicy.score` calls `candidate.rank` on every incident without an exception boundary (`backend/app/ml/policy/shadow_policy.py:98-113`). A candidate failure therefore blocks production recommendations despite being observational.

A missing production artifact selects the conservative ranking and marks degradation (`backend/app/ml/policy/shadow_policy.py:98-113`, `:165-178`; `backend/app/main.py:99-104`). Corrupt/incompatible production or candidate artifacts instead cause startup failure; `main.py` turns caught load errors into `AppError`, and deserialization exceptions outside `OSError`/`ValueError` escape (`backend/app/ml/policy/contextual_bandit.py:103-119`; `backend/app/main.py:77-96`). A corrupt reward model is reported healthy merely because the path exists (`backend/app/main.py:96-99`).

**Confirmed integrity and security gap, must fix:** registry checksums are unused and `joblib.load` deserializes before schema validation (`backend/app/ml/policy/contextual_bandit.py:103-113`; `backend/app/ml/reward/reward_model.py:113-128`). Verify the active registry checksum before deserialization, restrict artifact provenance, and degrade candidate failures independently from production.

### Chronological development holdback stays clear of test labels

`build_offline_incidents` loads only train and validation; `load_split` rejects other values and test labels require the Phase 8 acknowledgement (`training/train_reward_model.py:27-116`; `evaluation/dataio.py:68-111`). Events and incidents are chronological, and the latest configured fraction of validation incidents is excluded from bandit fitting (`evaluation/dataio.py:48-53`; `training/train_reward_model.py:35-116`; `training/train_bandit.py:25-49`). Split ordering and the holdout guard are tested (`tests/unit/test_leakage.py:34-48`). **Confirmed, acceptable limitation:** this is a development validation holdback, not the independent final test, and the report says so (`evaluation/evaluate_policy.py:93-104`, `:130-138`).

### Versioned assumptions are disclosed, but not carried with every counterfactual

`ActionEffects` requires an exact action map, INR, version, literal `explicit_counterfactual_assumptions` source, and notice (`backend/app/services/evaluation_service.py:32-62`). Reward outputs carry the version and per-action coefficients; observed rewards identify their source as observed outcome plus declared assumptions, and the evaluation report says effects are not observed treatment effects (`backend/app/services/evaluation_service.py:86-153`, `:181-204`; `evaluation/evaluate_policy.py:130-138`).

**Confirmed, non-blocking disclosure gap:** `RewardResult.assumptions` contains only `effect.model_dump()`, omitting the top-level notice, source, and currency despite the requirement to render the notice beside every counterfactual (`backend/app/services/evaluation_service.py:141-152`; `infrastructure/action_effects.yaml:1-5`; `.agent/IMPLEMENTATION_PLAN.md:611-620`). Carry that metadata in each result or enforce a versioned join at every renderer.

### Incident memory remains outside authorization

Memory evidence is marked `advisory_only`; prior reward and rejection affect only learned policy context (`backend/app/agents/tools.py:230-243`; `backend/app/ml/policy/shadow_policy.py:121-166`). `build_authorization_context` ignores `incident_memory` and accepts deterministic window, segment, impact, and similar-incident records (`backend/app/safety/evidence_grounding.py:74-225`). Memory can change ranking but cannot raise grounding, confidence, impact, role permission, or authorization.

### Safety failure paths lack regression coverage

The targeted suites pass: `14 passed` for `test_policy_promotion.py`, `test_reward_model.py`, and `test_leakage.py`. **Confirmed coverage gap:** no test exercises serving-policy swap after promotion/rollback, promoted artifact integrity, corrupt candidate isolation, failed publication plus replay, concurrent conflicting outcomes, or reward/memory consistency on conflicting replay.
