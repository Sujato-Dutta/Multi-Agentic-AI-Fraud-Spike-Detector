# Durable Phase 6 outcome learning and human-gated policy serving

Phase 6 closes the analyst-feedback loop with transactionally persisted decision, outcome, reward, memory, and outbox records, then serves only the DB-selected production policy behind deterministic safety and human authorization. `analyst.decision`, `analyst.outcome`, and `reward.calculated` now have stable durable identities and recoverable at-least-once dispatch. Promotion remains an explicit admin operation backed by frozen-holdback evidence and checksum-verified artifacts; candidate scores stay observational. No confirmed must-fix blocker remains in the reviewed Phase 6 scope.

**Watch for:** **confirmed (non-blocking)** at-least-once delivery can duplicate an event after broker acceptance but before the outbox row is marked published; **confirmed (non-blocking)** an outcome-handler failure preserves the Kafka offset but stops the unsupervised consumer task until restart; **confirmed (non-blocking)** reward weights and operational cost settings are persisted but lack one aggregate versioned economics identity.

**Verdict**: APPROVED

## High-level view

Each authoritative state transition and its event outbox row now share a database transaction. Decision recovery bridges the durable LangGraph checkpoint and relational decision through lease/CAS ownership, while outcome and reward replay use immutable IDs and canonical DB state.

Serving resolves the DB-active policy for every incident and caches only checksum-verified models. Promotion and rollback lock the registry, reject stale activation assumptions, verify artifacts, and are available only through explicit admin operations; a production artifact failure falls back to conservative human escalation.

Promotion evidence binds same-holdback candidate and production metrics to the candidate checksum, production identity, holdback digest, and action-effects version. The candidate is fit without the chronological validation tail used for evaluation, never accesses held-out test data, and remains shadow-only.

Historical memory can influence a learned recommendation but cannot authorize it. Final actions still require deterministic evidence/policy checks, role permission, and durable human review; authoritative outcomes are re-read before atomic reward and memory learning.

## Confirmed must-fix blockers

None.

## Acceptable operational limitations

**Confirmed — at-least-once duplicate window.** A broker-ack/DB-mark crash can republish the same stable envelope; downstream consumers must deduplicate by `event_id`.

**Confirmed — handler recovery requires restart.** Generic outcome-handler failures leave the offset uncommitted but terminate the current consumer task; Kafka preserves the event for restart recovery, while continuous recovery would require supervision, bounded retry, or a DLQ.

**Confirmed — reward economics lack one aggregate version.** Action effects are versioned and actual weights/costs are persisted, but changing those settings without bumping an assumptions identity makes replay fail closed against the immutable stored reward.

## Transactional decision-to-reward publication

```text
human review checkpoint
  -> resume reaches awaiting_outcome
  -> completed decision + resume audit + analyst.decision outbox

analyst outcome API
  -> immutable outcome + completed incident + audit + analyst.outcome outbox

analyst.outcome consumer
  -> canonical DB decision/outcome
  -> immutable reward + incident memory + reward.calculated outbox
```

`analyst.decision` is emitted only after the graph reaches the durable `awaiting_outcome` checkpoint. A crash after checkpoint advancement but before relational completion is recovered by matching the stored review and reconciling or continuing from that checkpoint; retry then commits the decision, audit, and `decision:<decision_id>` outbox row together. Repeated terminal requests call `enqueue_once`, so they can repair a missing event without changing its content.

`analyst.outcome` shares a transaction with the compare-and-set from completed decision to `outcome_recorded`, incident completion, and audit append. Identical replays reuse `outcome:<decision_id>` and the original outcome timestamp. `reward.calculated` shares a transaction with the unique reward and incident-memory upsert under `reward:outcome:<decision_id>:<assumptions_version>`; replay validates all immutable reward inputs before accepting the existing row.

The dispatcher commits conditional claim leases before I/O, retries failed sends with backoff, and makes expired claims recoverable. The producer uses all acknowledgements and Kafka idempotence, and the durable outbox ID becomes the envelope ID. **Confirmed (non-blocking):** a crash after broker acceptance but before `mark_published` can still duplicate delivery, so `event_id` remains the consumer deduplication key.

The outcomes consumer commits only after reward handling succeeds. **Confirmed (non-blocking):** generic handler exceptions leave the offset safe but escape `EventConsumer.run`; the retained event is replayed after process restart rather than by an in-process supervisor.

## DB-selected activation, evidence binding, and artifact fallback

`RuntimePolicyResolver.score` re-reads the registry's active version for every incident, so promotion and rollback affect all resolver instances. Models are cached by `(policy_version_id, artifact_checksum)`. Activation locks the policy row, checks the expected active version, retires the previous version, records the approver, and switches the registry pointer atomically; rollback only accepts a retired target and uses the same stale-activation guard.

Both the API dependency and `PolicyService` require admin permission for promotion and rollback. The only production activation call sites are those explicit service methods; the repository call in tests seeds a baseline. No candidate scoring path activates a version, and comparison output declares `automatic_promotion: false`.

The evaluator freezes the chronological validation tail, while candidate fitting excludes those incident IDs. Candidate and production are scored on the same holdback, whose IDs, start time, and selection rule are hashed into evidence alongside both metric sets, candidate checksum, production identity, and action-effects version. Promotion recomputes the evidence/holdback digests, validates the metric schema and safety/performance gates, verifies both artifacts, and rejects a concurrently changed production version.

Artifact bytes are SHA-256 checked before joblib deserialization, then validated for schema, feature order, action space, and assumptions version. Missing or corrupt production artifacts produce a degraded, human-escalation-first ranking; candidate corruption removes only the shadow result and cannot block production. The artifact-free built-in identity maps to that same fixed conservative behavior.

## Deterministic human authority and canonical learning

JWT identity is revalidated against the active DB user. Decision and outcome routes accept analyst, lead analyst, or admin roles; temporary defensive rules require lead/admin permission; policy lifecycle changes require admin. Review choices deterministically resolve to the recommended action, a modified action, `no_action`, or `human_escalation`, then rebuild authorization from deterministic evidence, impact, and actor role. The graph gate records `authorized: false`; only the persisted human-policy result can authorize an executable action, and approve/modify is blocked on any policy denial.

Outcome event payloads are not trusted as reward truth. Evaluation requires an `outcome_recorded` decision, compares the event's incident, choice, reason, recommendation, final action, and outcome with the canonical row, then calculates from that row. Reward replay must exactly match the unique stored inputs, and memory is written only with first reward creation in the same transaction. Conflicting outcomes, events, or reward replays fail closed instead of overwriting learned state.

**Confirmed (non-blocking):** reward arithmetic also depends on configured weights and analyst/delay costs. They are retained in components but not in the `action-effects-v1` idempotency identity, so changing them without a version bump leaves the Kafka event uncommitted on replay rather than mutating the prior reward.

## Shadow-only recommendations, advisory memory, and leakage controls

`ShadowPolicy.operative_action` and `production_ranking` always come from production or conservative fallback. Candidate scoring has an isolated exception boundary and is labeled `candidate_shadow_only`; `ResponseAgent` builds recommendations exclusively from `production_ranking` before deterministic policy and human gates.

Incident memory contributes similarity-derived reward and rejection features, so it can change a learned production recommendation. It cannot authorize an action, bypass grounding or role checks, activate a candidate, or skip human review.

Policy fitting excludes the selected validation-tail holdback, evaluation only scores the already-trained candidate there, and the evaluation protocol keeps the held-out test loader closed. Chronological memory features use only prior incidents, preserving the sequential advisory interpretation rather than feeding the current incident's outcome into its recommendation.

## Action-effect provenance and validation

The action-effect contract defines exactly six actions and records `action-effects-v1`, `explicit_counterfactual_assumptions`, INR, and a notice that values are assumptions rather than measured treatment effects. Counterfactuals retain per-action assumptions, financial components, weights, source, notice, currency, and version. Policy/reward artifacts reject cross-version loading; promotion evidence binds the version; observed reward rows, components, and events retain it. Observed rewards use reported prevented loss and false-positive cost, while analyst load/delay remain declared assumptions and unmeasured friction is explicitly zero.

The user-reported full suite is `50 passed`, with static and migration checks clean. This pass additionally ran reward/outbox, policy promotion/rollback, and policy authorization suites: `20 passed in 2.58s`. They cover authoritative-outcome tamper rejection, reward/memory idempotency, durable pending outbox rows, dispatch failure/recovery, stale evidence, serving activation/rollback, candidate isolation, and role denial. The end-to-end workflow also exercises a post-resume crash and recovery to one terminal decision.

**Confirmed test boundary (non-blocking):** local dispatch recovery uses fake failing/recording producers rather than a live broker crash at the acknowledgement boundary; the implementation therefore promises detectable at-least-once delivery, not exactly-once delivery.
