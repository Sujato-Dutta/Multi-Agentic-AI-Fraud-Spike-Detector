# Phase 7 observability/frontend and Phase 8 sealed evaluation

Phase 7 adds a poll-plus-WebSocket command center over one Prometheus catalog and an advisory PSI drift monitor; Phase 8 adds the single guarded held-out evaluation, eight in-process failure drills, and two submission checkers. The safety story holds up under inspection: no view presents a model as the authorizer or the source of a financial figure, the candidate policy is labelled shadow-only on every surface that mentions it, thresholds come from the frozen artifact rather than the test split, and drift writes gauges only. Three items are inaccurate or latently wrong rather than unsafe: the sealed-label read counter no longer matches the log format it parses, the documented Postgres-down failure case is neither drilled nor visible in the health strip, and two README lines claim a single sealed run that the same README later discloses as three reads.

**Watch for:** **confirmed** the access-log read counter greps `| 2` against a file that was reformatted to `## Read N` blocks, so a fourth read would announce itself as read 1 with no disclosure; **confirmed** Postgres-down is the one documented degradation case with no drill, and the dependency strip's only data source is the endpoint that 503s during that outage; **confirmed** README's "one sealed evaluation" / "single sealed run" framing understates the three disclosed reads; **confirmed (non-blocking)** the held-out policy comparison feeds the learned policies sealed labels and whole-split aggregates through context features that serving computes differently.

**Verdict**: NEEDS_CHANGES

## High-level view

The honesty protocol rests on three mechanisms: one guarded loader with one production caller and a negative-guard test, thresholds selected on validation and frozen into the artifact, and an append-only access log. Two are intact. The access log's *writer* was migrated to per-read Markdown blocks while its *reader* still counts table rows, so the mechanism that detects and discloses a repeat read is disarmed. Nothing published today is wrong — `results.json`, `report.md`, and the UI all say three reads — but the next run would print a false count.

The headline detection numbers are methodologically clean. Event matching, the causal EWMA detector baseline primed only on train+validation, and both operating points read from the frozen artifact keep sealed labels out of every tuning path. The policy-comparison section is weaker: its context vector is built from the window's own sealed `is_fraud` labels and whole-holdout means, and three of its features are defined differently again at serving time. Those numbers compare two rankings under offline-training feature semantics, not production behavior, and the report does not say so.

Degradation is visible for seven of eight documented cases, and the drills drive real components rather than asserting against stubs of the thing under test. Postgres is the exception: its server-side behavior exists but there is no drill, no test, and no client path that can surface it, because the dependency strip is fed exclusively by an endpoint that fails with Postgres while the declared `degradation` WebSocket message is never broadcast and the resilient `/api/health` endpoint is never called.

Drift reaches neither training nor policy activation by any path. The narrower issue is coverage: four of the five advertised monitored features can never be measured because the observation query selects only `risk_probability`.

README fidelity to `results.json` is machine-checked and passes, and the precision shortfall (0.6209 against a 0.90 validation floor) is stated three times with its cause. The overstatements that remain are about process, not numbers.

## The read counter and the log it parses have diverged

`run_heldout_evaluation` decides how many times the sealed labels have been read by counting Markdown table rows:

```python
previous_entries = (
    sum(1 for line in access_log.read_text(encoding="utf-8").splitlines() if line.startswith("| 2"))
    if access_log.exists() else 0
)
```

The same function then appends `## Read {previous_entries + 1}` with bullet fields. `ACCESS_LOG.md` states it was reformatted once from a table into per-read blocks, and a line scan confirms zero lines beginning with `|`. So `previous_entries` is now permanently 0. A fourth read would write `results.json` with `access_log_entries: 1`, render "Reads of the sealed labels so far: **1**", skip the `DISCLOSURE: this is read N` integrity note entirely, and append a second block titled `## Read 1`.

Everything published today is consistent — `results.json` carries 3, `report.md` says 3 and names the reason, README's deviations table says three, and the reports view renders the count with the disclosure notes underneath. The defect is that the tripwire is disarmed, and disarmed in the direction that produces a false honesty claim rather than a noisy one. Counting `## Read ` headings is the one-line fix; a JSON sidecar the generator owns would be sturdier than parsing prose it also writes. `--render-only` is genuinely read-free as the deviations table claims: it loads `results.json`, rewrites `report.md`, and adds no entry.

## Postgres is the documented case with neither a drill nor a display

The named failure cases in `agent.md` are primary fraud model unavailable, LLM/agent failure, Redis unavailable, streaming delay, unsupported AI claim, policy violation, and candidate policy underperforms; the plan's Phase 5 matrix adds Postgres down and asserts "every one of the eight failure cases produces a visible degraded state plus a metric". `failure_drills.py` runs eight drills, but the eighth is `policy_artifact_corrupt` — a real and useful case, just not the documented one. Postgres down has no drill, and a grep of all 14 test files finds no coverage of `postgres_down`, `database_unavailable`, or the stream-buffering path.

The server-side behavior is implemented twice: `TransactionService._database_unavailable` marks `postgres` down, increments `postgres_down`, buffers to the stream, and raises a 503; the app-level `SQLAlchemyError` handler does the same for any route. What is missing is delivery to the operator:

```text
DegradationState (server knows postgres is down)
   |
   +-- /api/metrics/summary  --> touches Postgres --> 503, no snapshot returned
   |                                  ^ the only source the shell reads
   +-- /api/health           --> probes Postgres, reports, returns 200 + snapshot
   |                                  ^ declared in api.js, never called
   +-- WebSocketMessage type "degradation"
                                      ^ declared in schemas.py, never broadcast
```

`refreshShared` catches the 503, records the error, fires a "Metrics unavailable" toast, and leaves `state.dependencies` untouched, so the strip keeps rendering the last healthy snapshot for the duration of the outage. `handleShellMessage`'s `message.type === "degradation"` branch is dead code — no backend call site broadcasts that type. The transient toast is the only signal, and its detail text ("Postgres is unavailable; retry this write safely") reads oddly on a read path. Calling `api.health()` when the summary fails resolves this with the endpoint that already exists.

## The drills exercise real components

Running four in-process confirms they are not stub assertions. `fraud_model_missing` drives `ResilientFraudScorer` through both missing artifacts into rule scoring (`degraded=True`, `score_space=deterministic_conservative_rule_score`, risk 0.75). `redis_down` drives `CacheService` against a Redis double where every method raises, and the emitted `redis_degraded` warnings with `fallback=True` show the fallback path actually taken before the assertion on `degraded`/`down` plus a served read. `llm_unavailable` drives `StructuredLLMGateway` through all three tiers (`primary/secondary/economy:TimeoutError` logged in order) into the deterministic template. `stream_down` asserts the `stream_unavailable` `AppError` code and `stream` down.

Two are simulations rather than injections, which is defensible with no Docker available: `stream_down` injects an `UnreachableProducer` whose `start` raises rather than relying on the unreachable `127.0.0.1:1` it also configures, and `policy_artifact_corrupt` uses a production ranker that raises.

## Sealed labels stay out of every tuning path, but not out of the policy comparison

The tuning-path audit is clean. `select_operating_points` runs on validation during training and both thresholds are persisted into the artifact; `evaluate_fraud_model` reads `predictor.thresholds[operating_point]`, so reporting a second operating point costs nothing in leakage. The detector replay primes on train+validation only, chronologically before the test split, and `leakage_check` asserts strict `train_end < validation_start < validation_end < test_start` plus label/ID absence from the model matrix. `load_test_holdout` and `load_test_benign_events` have exactly one production caller. Event matching uses a fixed 30-minute grace, matches the first unmatched event, and counts repeat alerts inside a matched event as continuations — excluded from both precision terms, disclosed in the report table, and zero on this run.

The policy section is where sealed data reaches the learned components. `_holdout_incidents` merges `holdout.labels` and builds:

```python
"historical_segment_fraud_rate": float(rows["is_fraud"].mean()),
"agent_confidence": 0.0,
"grounding_score": 0.0,
"segment_breadth": float(min(1.0, len(rows) / max(len(holdout.features), 1))),
"density_lift": float(np.mean(probabilities) / max(split_density, 1e-9)),
```

`split_density` and `hourly_volume` are whole-holdout means, so lift features look ahead within the test split — unlike the detector, which uses a causal EWMA baseline. At serving time `shadow_policy` supplies `historical_segment_fraud_rate` from `baseline.expected_high_risk_rate` (a predicted rate, not a realized one), passes the true grounding score into both confidence features, and computes `segment_breadth` as `support / window transaction_count`. `train_reward_model` uses the label mean too, and pins `segment_breadth` at 1.0 — a third definition.

Consequence: the reported production ₹-916.75 against candidate ₹-1,808.80 compares two rankings under offline-training feature semantics with one oracle input, and should not be read as what either policy would do in production. Nothing is promoted from it (`automatic_promotion: false`, admin-gated activation), the candidate was fit on development data only, and the headline transaction, event, and business metrics do not touch these features. Worth disclosing because read 2 of the sealed labels was spent fixing exactly this context vector: the fix aligned the report with *training*, and the serving mismatch remains.

## Drift raises alerts and nothing else

`DriftMonitor.refresh` computes PSI, sets `DRIFT_PSI` and `DRIFT_ALERT_ACTIVE`, and returns; `snapshot()` hardcodes `auto_retrain: false` and `auto_policy_change: false`, and the route repeats both in its unavailable branch. A repository-wide search for retrain or policy-change triggers finds only those literals, the UI copy, and the plan text — no training invocation, no `activate`, no threshold mutation anywhere downstream of a PSI result. PSI raises rather than returning a misleading 0.0 when a sample is too small, surfaced as `insufficient_observations` with `alert=False`.

The coverage gap is that `_recent_scores` only ever returns `risk_probability`:

```python
select(FraudScore.risk_probability).order_by(...).limit(window)
```

while `MONITORED_FEATURES` names five and `from_training_reference` builds a reference for every one present in the training frame. So `amount_inr`, `txn_velocity_1h`, `ip_risk_score`, and `geo_distance_km` always take the exception branch: psi 0.0, `DRIFT_PSI` never set for them, `DRIFT_ALERT_ACTIVE` pinned at 0. The panel shows them at 0.000 with the reason string attached, which is honest at the row level but reads as four measured-and-stable features to anyone skimming. Either join the feature columns into the observation query or advertise one feature.

## The frontend's safety copy matches the backend contract

The authority claim is stated on every surface that could imply otherwise: the landing page ("a deterministic policy engine — never a language model — authorize every action"), the policy gate panel ("Model output is advisory only"), the response comparison heading ("Production policy ranking; the model only explains it"), the segment panel ("Deterministic discovery, no model involved"), and the impact panel ("No language model produces a number in this system"). Shadow-only labelling is consistent across the three surfaces that mention the candidate — models page badge and footer, agent timeline (`candidate … (shadow only)`, "Candidate output is observational; only the production ranking is operative"), and the report view ("Candidate action (shadow)"). Approve and Modify disable themselves with an explanatory note when `checkpoint_durable` is false while Reject and Escalate stay live, which is the right asymmetry.

Two places let the view drift from the contract rather than derive from it. The hypotheses stage hardcodes a positive "supported" badge and, when the list is empty, asserts "All hypotheses were stripped by deterministic grounding." The API does filter to supported claims and stamps each with `verification_verdict`, so the badge is correct today but ignores the field that would keep it correct; and an empty list is also what you get when the LLM produced no hypotheses, or when `_verification_verdicts` fail-closes because the verification payload count is not exactly one — so the explanation is asserted rather than known. Separately, `renderResponseComparison` can print "review waived" when `requires_human_review` is false, a state the backend forces true, so the branch exists only to contradict the safety model if that contract ever changes.

## Hardcoded values: metrics clean, one policy threshold not

`check_frontend.py` passes across 32 files with no missing references and no metric literals. Absent data degrades to statements rather than numbers: the report page reads everything from `results.json` through `/api/metrics/heldout` and swaps in "Held-out evaluation has not been run" with the expected path when `available` is false, each panel has its own `emptyState`, formatters return "—" for non-finite input, the trend refuses to plot under four points and says why, and counters set the true value immediately under `prefers-reduced-motion`.

Two exceptions. The grounding floor `0.7` is hardcoded in `agents.js` (badge tone) and `investigation.js` (the "escalation is forced" toast) while `infrastructure/policies.yaml` owns `grounding_score_floor: 0.70`; the guard's regex only matches `precision|recall|pr_auc|roc_auc|f1|net_risk_benefit|psi`, so a drift between YAML and UI would pass every check and mislabel a gate. And `reports.js` renders `integrity.access_log_entries ?? 1` as "Evaluation runs", defaulting an honesty-critical field to a plausible number instead of "—" — the one place the interface would invent a value.

## README fidelity is machine-checked; the overstatements are procedural

`verify_submission.py` passes: 18 quoted metrics matched against `results.json`, no untraceable numbers outside a declared constants allowlist, 14/14 test files, no pinned requirement specifiers, no project `pyproject.toml`. The derived figures reconcile — analyst review 750 = 3 alert windows × ₹250, friction 6,520 = 163 false positives × ₹40, both flagged as assumptions in the table and in the panel copy.

The precision shortfall is not softened anywhere: 0.6209 sits in the results table, a bolded caveat states it fell below the 0.90 validation floor, that the threshold was frozen before the run and not re-tuned, which `difficulty=hard` spike families caused it, and that PR-AUC 0.9485 localizes the loss to threshold placement rather than ranking; it reappears under known limitations.

What overstates is process. "Every metric in this README is copied from `reports/heldout_test/results.json`, produced by one sealed evaluation of the test holdout" and the "Held-out results (single sealed run)" heading both assert a single run; the deviations table 200 lines later discloses three reads, and `report.md` leads with "Reads of the sealed labels so far: 3". Metrics were identical across reads and only the generator changed, so no number is affected — but the strong claim is at the top and the correction is in a table further down. The second is property 2: "every dependency has a defined, *visible* failure behaviour. All eight documented cases are exercised by `scripts/failure_drills.py`: **8/8 pass**" — eight drills pass, but the set is not the documented set, and the omitted case is Postgres.
